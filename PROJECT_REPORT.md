# ShopWise 360 — Project Report

## Architecture Overview

**Full-stack retail analytics platform** with four roles: Customer, Retailer, Supplier, Admin.

```
Client (React 18 + Vite + Tailwind CDN + Recharts) — dev port 3001
  ↕ Axios + JWT Bearer
Server (Node.js / Express, port 5000)
  ↕ mysql2 (promise pool, 10 connections)
  ↕ axios (ML proxy)
MySQL 8  (shopwise360 database, 15 tables)
  ↕ mysql-connector-python
ML Service (Python 3 / Flask, port 6000)
  Scikit-learn 1.5 · Pandas · NumPy
```

> **Port note:** the Vite dev server runs on **3001** because port **3000 is owned by
> Windows IIS/HTTP.sys** (a system service) on this machine and cannot be freed without
> admin rights. All fan-out (API, socket, proxy) still targets `localhost:5000` /
> `localhost:6000`, so no config elsewhere changed.

### Request flow
1. Client sends requests with `Authorization: Bearer <JWT>`.
2. Express middleware verifies JWT, rejects `type:'refresh'` tokens, and attaches `req.user = { id, role, email }` (legacy no-`type` tokens still accepted).
3. Role-specific routes check `authorize('retailer', 'admin')` etc.
4. Dashboard / ML proxy routes call MySQL and/or the Flask microservice.
5. Flask reads directly from the same MySQL database (no REST between server→ML).
6. Node server proxies Flask responses back to the client.

## Database Design

17 tables in `shopwise360` (16 + `refresh_tokens`). Key design decisions:

| Table | Purpose | Notable choices |
|-------|---------|-----------------|
| `users` | Single user table for all 4 roles; ENUM('customer','retailer','supplier','admin') | Avoids separate auth tables per role |
| `retailers` / `suppliers` | 1:1 profile extension (FK→users, ON DELETE CASCADE) | Keeps auth minimal; profile is optional per role |
| `products` | Core catalog; FK to categories (SET NULL) + suppliers (SET NULL) | SET NULL on FK means products survive category/supplier deletion |
| `inventory` | Junction: product × retailer with quantity + threshold | UNIQUE(product_id, retailer_id) prevents duplicates |
| `orders` / `order_items` | Header + line-items pattern | Supports multi-product orders; header stores `coupon_id` + `discount_amount` (FK→coupons ON DELETE SET NULL) |
| `coupons` | Discount codes, platform-wide or per-retailer (`retailer_id` NULL = any store) | `discount_type` ENUM('percent','flat'), optional `min_order_value` + `max_discount` cap, `usage_limit`/`used_count` race-safe via `FOR UPDATE` at checkout |
| `sales_transactions` | Pre-computed per-line profit/revenue (denormalized from order_items + products) | Avoids recomputation in dashboard queries |
| `stock_alerts` | Generated by cron + inventory update; `resolved` flag | Audit trail for low-stock events |
| `reviews` | Customer ratings (1-5) + comment per product; UNIQUE(customer_id, order_id, product_id) | One review per purchased line prevents spam |
| `wishlists` | Customer save-for-later; UNIQUE(customer_id, product_id) | Idempotent add |
| `refresh_tokens` | Opaque refresh-token store (SHA-256 hash only, no plaintext); UNIQUE(token_hash), FK→users CASCADE | Enables rotation + reuse-detection family revoke; tokens expire |
| `recommendations_log` | ML recommendation calls **only when the model was actually (re)computed** (`X-ML-Computed: true`) | Cache hits write nothing — keeps the log lean |
| `demand_predictions` | ML demand rows written **only on recompute**, upserted via `UNIQUE uniq_demand_day (retailer_id, product_id, prediction_date)` | Bounded at one row per product per day regardless of dashboard loads |
| `audit_log` | Admin action trail: `actor_id`/`actor_role`, `action`, `entity_type`/`entity_id`, `details` JSON, `created_at` | Fire-and-forget writer that never breaks the triggering request; written on coupon/product create+delete, order status changes, model retrains |

**Indexes:**
- `idx_inventory_retailer` on `inventory(retailer_id)`
- `idx_sales_product` on `sales_transactions(product_id)`
- `idx_sales_retailer_date` on `sales_transactions(retailer_id, sold_at)`
- `idx_orders_customer` on `orders(customer_id)`
- `idx_reviews_product` on `reviews(product_id)`
- `idx_wishlists_customer` on `wishlists(customer_id)`
- `uniq_demand_day` UNIQUE on `demand_predictions(retailer_id, product_id, prediction_date)`
- `fk_orders_coupon` FOREIGN KEY on `orders(coupon_id)` → `coupons(id)` ON DELETE SET NULL
- `idx_audit_action` on `audit_log(action)`; `idx_audit_entity` on `audit_log(entity_type, entity_id)`; `idx_audit_created` on `audit_log(created_at)`

## ML Microservice

Models are **persisted with joblib** (`ml-service/models/`) and lazily refreshed: a
12-hour TTL (`MODEL_MAX_AGE_SECONDS=43200`) marks a model stale; any stale/missing
model is **re-trained on the next read** and served fresh (response header
`X-ML-Computed: true`). Cache hits within the TTL serve the artifact instantly with
`X-ML-Computed: false` and write no audit rows.

| Endpoint | Algorithm | Evaluation | Cold-start handling |
|----------|-----------|------------|---------------------|
| `/recommend?customer_id=X` | Item-based collaborative filtering (cosine similarity on customer-product interaction matrix) | Leave-one-out **precision@k** eval `/model-health` | Falls back to top-N popular products by total units sold |
| `/predict-demand?retailer_id=X` | Per-product linear regression (day-index → quantity, 7-day horizon) | Last-day holdout **MAE** trained into model metadata | Products with <2 data points use avg_daily × 7 |
| `/retrain` (POST) | Triggers rebuild of `recommend` +/or `demand` (per retailer or all) | Returns per-model metrics + metadata on completion | — |
| `/model-health` (GET) | Serializes the model registry (recommend + per-retailer demand) | `{ demand: { models: [{ retailer_id, fresh, age_seconds, meta, metrics }] }, recommend: { fresh, age_seconds, meta, metrics }, max_age_seconds }` | — |

Audit rows (`recommendations_log` / `demand_predictions`) are written **only** when a
read forced a recompute, and demand rows are deduped by `uniq_demand_day`, keeping both
tables bounded regardless of dashboard load frequency.
